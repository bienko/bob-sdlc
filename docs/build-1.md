## **i. Why this matters**

![type:video](./_videos/3 Planning and Scaffolding the Application [Bob SDLC L3].mp4)
!!! note ""
    Christopher Bienko *(AI Enablement GTM Product Manager)* provides an overview of the *Planning and Scaffolding the Application* module for the hands-on enablement. **<a href="https://bienko.github.io/bob-sdlc/build-1/" target="_blank">[2 min]</a>**

Before generating a single line of code, IBM Bob should understand what it is being asked to build. Scaffolding an application without that context tends to produce boilerplate that has to be thrown away — plausible React code that does not match the repository, the workshop goals, or the delivery workflow.

Modern GitHub-driven engineering follows the opposite pattern. A clear plan is drafted first. Component boundaries, service layers, state management, and validation strategy are agreed up front. Only then does implementation begin, and every file that lands in the repository maps to a decision that was made deliberately.

!!! note ""
    The application will track IBM and four major competitors — Microsoft, Oracle, SAP, and Salesforce — using Yahoo Finance data across three time windows: current day, last 7 days, and last quarter.

In this module, you will use IBM Bob to inspect the workshop starter repository, produce a structured implementation plan for a React finance dashboard, and then scaffold the application in a shape that supports later GitHub-driven feature evolution.

Pay attention to how Bob frames the greenfield task as an engineering exercise— folder layout, data-service boundaries, error handling, test strategy —rather than a code-generation shortcut.

## **ii. Planning and scaffolding the application**

!!! warning "ATTENTION: NON-DETERMINISTIC WORK AHEAD"
    Bob's responses are **non-deterministic**, so the plan and file layout produced in your IDE may differ from those shown here. It's also possible that some architectural choices — folder names, chart library, state management approach — will vary from run to run.

    IBM Bob is powered by generative AI and LLMs, and a defining trait of these systems is that they are *non-deterministic* — unlike the *deterministic* tools most developers are accustomed to. In practice, that means the same prompt can produce different code from one run to the next. This is both a strength and a quirk of the technology, and it is something to work *with* rather than against.

    **All this is to say: *Your results ahead may vary.*** The key takeaway from these workflows is that you understand how to effectively utilize each of Bob's Modes and where their strengths are best applied. Whether or not you arrive at the exact same codebase at the end is of less importance. Bob will ensure either way that your application works and delivers more-or-less what you asked for. The exact implementation and steps that Bob takes to arrive at that result, however, may differ from the steps documented here.

The starter repository contains only the workshop scaffolding: documentation, a pull request template, and a CI workflow. Everything else, including the React project itself, will be generated by Bob.

**You will move through this module in two phases.** First to ask Bob to analyze the repository and propose an implementation plan. Then to approve the plan and let Bob scaffold the application sub-task by sub-task. By the end of the module, the app will run locally in mock mode and render its first dashboard view.

## **iv. Key takeaways**

- Planning first, then scaffolding sub-task by sub-task, produces a codebase that matches intent (not just plausible boilerplate)
- IBM Bob can turn a natural-language brief into a structured implementation plan with clear component and service boundaries
- Sub-task sequencing makes the scope of each generation step explicit before code is written and gives the developer a clear approval gate at every stage
- A mock-data seam lets the app run and be validated offline before any external integration is added
- Local validation (lint + tests + build) belongs inside the scaffold plan as its own sub-task
- Developers remain responsible for reviewing the plan, approving each sub-task, and validating the generated output
